# TCL T7H 语音接入验证（2026-10-11）

## 结论

**已实测完成一次实时「小T语音搜索 → 自定义 TV 应用搜索 API → 应用结果页」闭环，无需 USB 或 root。**

这不是原厂 ASR 全文拦截，不是原厂执行前接管，也不是任意自然语言任务系统。验证结束后已停止桥接并卸载临时组件，尚未部署常驻功能。

## 环境与约束

- 用户电视：TCL T7H；ADB 设备 `192.168.1.22:5555`；Android 11/API 30。
- 固件：`V8-T653T11-LF1V487`；生产 user 构建，bootloader/vbmeta 锁定，未取得 root。
- 原厂助手：`com.tcl.walleve`；原厂影视搜索：`com.tcl.wholenetsearch`。
- 目标应用：`com.elicc.android.tv`；局域网 HTTP API：`http://192.168.1.22:9978`。
- HDMI 不是 ADB 通道；本次 Type-C 连接未枚举出 USB ADB 设备。网络 ADB 足以完成以下实验。

## 已验证链路

```text
小T小T唤醒 → 原厂识别/理解 → 原厂搜索结果页
        → 临时无障碍服务读取指定资源 ID
        → Mac 上的短时 Python 桥接进程
        → ADB 将目标应用带到前台
        → POST /action，do=search，word=片名
        → 目标应用搜索结果页
```

临时观察 APK 不申请录音或网络权限，只观察助手与原厂搜索包。示范脚本只允许固定设备、固定目标应用及搜索动作；识别文字仅作为表单数据，不拼入 shell。拒绝「没有找到／为你推荐」一类标题；每次最多执行一次，限制运行时长。它也会响应人工打开的同类搜索页，不能证明事件必然来自语音。

### 应用源码依据

- `app/src/main/java/com/fongmi/android/tv/server/process/Action.java`：`onSearch` 发布搜索事件；`onControl` 提供 play/pause/stop/prev/next 等，后者依赖活跃的 PlaybackService。
- `app/src/leanback/java/com/fongmi/android/tv/ui/activity/HomeActivity.java`：接收 SEARCH 事件，支持 `ACTION_SEARCH` + `SearchManager.QUERY`。
- 本轮没有实测语音播放控制、自动选源/选片、跨应用任务或多步 Agent。
- 当前 `tv-agent` 元数据解析接口不能等同于完整自然语言任务路由器。

## 可落地方案与选择

### A. 保留原厂唤醒，优先做影视搜索（已有实测依据）

将临时桥接做成正式功能：监听明确的原厂页面字段，去重、等待稳定结果、调用本应用已有能力、处理前台切换。当前验证需要常开的 Mac + 网络 ADB；未来可研究把读取与 HTTP 请求放到电视辅助 APK 内，是否能稳定后台启动目标应用仍需单独验证，不能声称已脱离电脑。

局限：原厂会先执行，可能闪现原厂页面/播报；页面结构和固件变化会影响兼容性；不能覆盖未进入搜索页的命令；推荐性标题不等于原句。一次成功不是长期稳定性测试。

### B. 任意自然语言任务：独立语音入口（推荐的整体方案，尚未实测）

```text
电脑/NAS 的麦克风或独立语音终端
 → 自定义唤醒词或按键录音
 → ASR
 → 自定义服务/自然语言意图解析
 → 受约束的动作路由
 → TV 的搜索、播放控制等 API
```

这样不依赖 TCL 暴露识别全文，可保留自由表达，但能执行的任务仍取决于已接入的工具/API。用不同唤醒词可避免同时触发原厂；涉及购买、删除等操作要显式确认。ASR 本地还是云端需结合隐私、延迟、费用选择。实际麦克风、识别服务和任务服务尚未选定/接通，不能宣称此方案已完成。

若要求直接使用电视远场麦克风或遥控器麦克风，则还须验证普通应用的录音权限、设备路由和与 OEM 助手的抢占关系。本次没有验证这些条件。

### C. 原厂完整接管（未打通）

静态代码里存在 ASR 文本分发、NLP 前置处理和第三方权限接口；但未取得对应运行时权限/进程注入能力。厂商开放授权可能是一条路；root/hook 则需该精确固件的可靠方法，当前没有。不能把相似型号的刷机教程当成适配证据，不建议盲目刷机来追求此目标。

## 验证产物与恢复

本机临时产物位于 `/tmp/tcl-voice-inspect/`，系统可能清理此目录：

- `search_bridge.py`：单次、限时、默认 dry-run 的概念验证脚本。
- `bridge-live-result.log`：流浪地球实时事件与 HTTP 调用记录。
- `observer/`：临时观察组件源码、构建产物和限定范围的事件记录。
- `observer/after-phrase.log`：自然表达被 OEM 改写为推荐标题的反例。
- `probe-result.log`：早先 Binder 权限探测结果。
- `restoration.json`：最终恢复检查。

完成后已停止所有本次 logcat/桥接进程，卸载 `com.elicc.voiceobserver` 与此前的 `com.elicc.voiceprobe`，恢复测试前无障碍服务列表与开关，恢复空的 `log.tag.aiyf.asr`。YLog 定向级别已设回默认 Debug；没有写入持久 YLog 属性，临时进程内 handler 不等于已删除。没有 root、刷机、禁用原厂助手或修改产品代码。

ARTEMIS 的 UiAutomation 会暂时抑制普通无障碍服务，且关闭时可能重写无障碍设置。验证过程中先释放该观察连接，再启用诊断服务；最终再次恢复设置并确认原厂助手服务已绑定。后续复现实验需避免一边持续使用 UiAutomation，一边期待无障碍观察组件工作。

本次新增的是本报告；不涉及产品重构或依赖变更。剩余风险为 OEM 先执行、页面兼容性、ADB 常驻连接和语音输入不完整。正式部署前需补充重复命令、超时、网络断连、重启恢复、误触发和前后台竞争测试。
